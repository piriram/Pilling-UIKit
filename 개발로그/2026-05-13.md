## 세션 1. 복약 버튼 탭 후 캘린더 셀 색상 변경 지연 5초+ 수정

한 줄 요약:
- 복약 버튼 탭 후 캘린더 셀이 초록색으로 바뀌는 데 5초 이상 걸리던 문제를 Optimistic UI Update로 해결했다.

## 1. 결론 (What / Product)

- 오늘 만든 결과물:
  - `CycleRepository.swift`: `updateRecord` / `saveCycle` / `updateScheduledTimes` 3곳에서 `WidgetCenter.reloadAllTimelines()` 호출 순서 변경
  - `DashboardViewModel.swift`: `takePill()`에 Optimistic UI Update 구현, `buildOptimisticCycle()` 추가
- 전/후 변화: 버튼 탭 후 셀 색상 변경까지 5초+ → 탭과 동시에 즉시 반영
- 수치 또는 범위: UI 지연 5초+ → 0ms (체감 지연 없음)

## 2. 배경 (Why / 3C)

### Customer

- 누구를 만족시켜야 했는가: Pilling 사용자
- 그들이 원하는 것은 무엇이었는가: 복약 버튼을 누르면 캘린더가 즉시 초록색으로 바뀌어야 함

### Company

- 프로젝트의 현재 목표: App Store 배포 품질 안정화
- 해결해야 할 문제: 복약 기록 후 UI 피드백 지연으로 인한 UX 저하
- 내 기여 지점: 원인 진단 + Optimistic Update 패턴 적용

### Competitor

- 기존 방식의 한계: CoreData 저장 완료 후 `WidgetCenter.reloadAllTimelines()`를 동기적으로 호출하고, 그 이후에야 `observer.onNext()`를 emit해 UI 업데이트가 트리거됨
- 이번에 선택한 방향: 버튼 탭 시 즉시 낙관적으로 UI 업데이트, CoreData 저장과 위젯 업데이트는 비동기로 처리

## 3. 실행 (How / 4P)

### Product

#### 원인 분석

- 증상: 복약 버튼 탭 후 5초 이상 캘린더 셀 색상 미변경
- 사용자 추측: 네트워크 응답 이후에 UI 업데이트가 발생한다
- 실제 원인: `WidgetCenter.shared.reloadAllTimelines()`가 내부적으로 XPC 통신(앱 ↔ 위젯 익스텐션 프로세스 간 통신)을 사용하며, 메인 스레드에서 호출 시 블로킹 지연이 발생함. 이 호출이 `observer.onNext()` 전에 위치했기 때문에 UI 업데이트 자체가 지연됨

#### 수정 1: CycleRepository — WidgetCenter 호출 순서 변경

```swift
// 수정 전
try context.save()
recordWidgetRefreshRequest(reason: "updateRecord")
WidgetCenter.shared.reloadAllTimelines()  // ← UI 업데이트 전에 XPC 블로킹
observer.onNext(())
observer.onCompleted()

// 수정 후
try context.save()
observer.onNext(())   // ← UI 먼저
observer.onCompleted()
DispatchQueue.main.async { [weak self] in
    self?.recordWidgetRefreshRequest(reason: "updateRecord")
    WidgetCenter.shared.reloadAllTimelines()  // ← UI 이후 비동기
}
```

`saveCycle()`, `updateScheduledTimes()`에도 동일 패턴 적용 (총 3곳)

#### 수정 2: DashboardViewModel — Optimistic UI Update

CoreData 저장을 기다리지 않고, 버튼 탭 시 즉시 상태를 계산해 UI에 반영:

```swift
func takePill() {
    guard let cycle = currentCycle.value else { return }
    let takenAt = Date()

    // 즉시 UI 반영
    if let optimisticCycle = buildOptimisticCycle(from: cycle, takenAt: takenAt) {
        currentCycle.accept(optimisticCycle)
        updateItems()
        updateDashboardMessage()
        updateCanTakePill()
    }

    // 실제 저장은 비동기로
    takePillUseCase.execute(cycle: cycle, settings: settings.value, takenAt: takenAt)
        .subscribe(
            onNext: { ... },  // 성공: 실제 cycle로 교체
            onError: { ... }  // 실패: 원본 cycle로 롤백
        )
        .disposed(by: disposeBag)
}
```

`buildOptimisticCycle()`은 `TakePillUseCase`와 동일한 상태 계산 로직(takenTooEarly / taken / takenDelayed)을 사용해 즉시 cycle을 생성한다.

### Price

- 만족 신호: 탭과 동시에 셀 색상 변경 (체감 지연 0)
- 저장 실패 시 롤백 처리 포함으로 데이터 정합성 보장
- `WidgetCenter` 블로킹 제거로 다른 저장 경로(saveCycle 등)도 동시에 개선

### Place

- `DashboardViewModel.takePill()` — 복약 버튼 탭 핸들러
- `CycleRepository.updateRecord/saveCycle/updateScheduledTimes` — CoreData 저장 후 위젯 업데이트 경로

### Promotion

- `WidgetCenter.shared.reloadAllTimelines()`는 문서상 non-blocking이지만 실제로는 XPC 통신으로 인해 메인 스레드에서 호출 시 블로킹될 수 있다. UI 업데이트 이후 비동기로 처리해야 한다
- Optimistic UI Update는 저장 성공률이 높고 레이턴시가 길 때 UX를 크게 향상시키는 패턴이다

## 4. 3화 점검

### 수치화

- UI 지연: 5초+ → 0ms
- 수정 지점: 4곳 (CycleRepository 3곳 + DashboardViewModel 1곳)

### 구체화

- 네트워크 문제로 추측했지만, 실제 원인은 위젯 업데이트 XPC 블로킹이었다. 코드를 직접 추적해서 원인을 특정했다
- `observer.onNext()` 전후 한 줄 차이가 5초의 UX 차이를 만든다

### 행동화

- `takePill()` → `TakePillUseCase` → `CycleRepository` → `CoreDataManager` 전체 체인을 순서대로 읽으며 블로킹 지점 탐색
- `WidgetCenter` 호출 위치 확인 → 순서 변경 → Optimistic Update 추가

## 5. 배운 점 / 인사이트

- `WidgetCenter.shared.reloadAllTimelines()`는 XPC 통신을 사용하며 메인 스레드에서 동기적으로 호출하면 수 초 단위의 블로킹이 발생할 수 있다. 항상 UI emit 이후에 비동기로 호출해야 한다
- Optimistic UI Update는 "저장 성공 가능성이 높다"는 가정 하에 UX를 즉각적으로 만드는 패턴이다. CoreData처럼 실패율이 거의 없는 저장소에 적합하다. 실패 시 롤백 처리를 반드시 포함해야 한다
- RxSwift Observable chain에서 `observer.onNext()` 이전에 블로킹 작업을 두면, 그 블로킹 시간 전체가 UI 지연으로 나타난다

## 세션 2. 복약 기록 시트 버그 2개 수정 + 서버 응답 폴백 처리

한 줄 요약:
- 시트가 열리자마자 onStatusUpdate가 발화되는 버그와, updateState 실패 시 UI가 롤백되지 않는 버그를 함께 수정했다.

## 1. 결론 (What / Product)

- 오늘 만든 결과물:
  - `StatusSelectionView.swift`: `setInitialSelection`에서 relay 직접 방출 코드 제거
  - `DashboardViewModel.swift`: `updateState` 에러 시 이전 cycle 롤백 + `showStatusUpdateError` relay 추가, `autoMarkPastScheduledAsMissed` / `reloadSettings` onError 추가
  - `DashboardViewBindingManager.swift`: `showStatusUpdateError` 구독 + `onStatusUpdateError` 콜백
  - `DashboardViewController.swift`: 에러 알림 연결
- 전/후 변화: 시트 열릴 때 불필요한 onStatusUpdate 즉시 발화 제거 / 복약 상태 변경 실패 시 사용자에게 에러 알림 + UI 롤백
- 수치 또는 범위: 수정 파일 4개

## 2. 배경 (Why / 3C)

### Customer

- 누구를 만족시켜야 했는가: Pilling 사용자
- 그들이 원하는 것은 무엇이었는가: 캘린더 셀 탭 → 시트 열기 → 상태 변경이 정확하게 동작해야 함

### Company

- 해결해야 할 문제:
  1. 시트가 열리는 순간 `onStatusUpdate`가 발화되어 상태가 엉뚱하게 덮어씌워짐
  2. `updateState` UseCase 실패 시 UI가 변경된 채로 남아 데이터 불일치 발생
  3. 서버 응답 실패 시 조용히 무시되는 구독들

### Competitor

- 기존 방식의 한계:
  1. `setInitialSelection`이 UI 초기화를 위해 relay를 직접 방출했지만, 그 relay가 `dismissTrigger`에 연결되어 있어 시트 열릴 때 즉시 dismiss + onStatusUpdate 발화
  2. `updateState` onError에서 print만 처리, 롤백 없음
- 이번에 선택한 방향:
  1. `ViewModel.init`에서 `selectedStatus = initialStatus`로 이미 초기화되므로 relay 방출 불필요 → UI 표시(`selectButton`)만 남김
  2. `takePill` 에러 처리 패턴과 동일하게 이전 cycle로 롤백

## 3. 실행 (How / 4P)

### Product

#### 버그 1: setInitialSelection relay 방출 → 즉시 dismiss

발화 경로:
```
output.initialButtonTag (Driver.just → 구독 즉시 방출)
  → statusSelectionView.setInitialSelection(buttonTag:)
    → notTakenTapped.accept(()) / takenTapped.accept(()) 등
      → DashboardSheetViewModel의 statusTapped 발화
        → dismissTrigger 발화
          → onDataChanged → onStatusUpdate 즉시 호출
```

`DefaultDashboardSheetViewModel.init`에서 `self.selectedStatus = initialStatus`로 이미 초기화되므로 relay 방출 자체가 불필요했다.

```swift
// 수정 전
func setInitialSelection(buttonTag: StatusButtonTag) {
    selectButton(tag: tag)
    switch buttonTag {
    case .notTaken: notTakenTapped.accept(())  // ← dismissTrigger 발화
    ...
    }
}

// 수정 후
func setInitialSelection(buttonTag: StatusButtonTag) {
    guard tag >= 0 else { return }
    selectButton(tag: tag)  // UI만 업데이트
}
```

#### 버그 2: updateState 에러 시 롤백 없음

```swift
// 수정 전
onError: { error in
    print("❌ UseCase 에러: \(error)")  // UI 롤백 없음
}

// 수정 후
onError: { [weak self] _ in
    guard let self = self else { return }
    self.currentCycle.accept(cycle)   // 이전 cycle 복원
    self.updateItems()
    self.updateDashboardMessage()
    self.updateCanTakePill()

```

#### 폴백 누락 추가

- `autoMarkPastScheduledAsMissed`: `onError: { _ in }` 추가 (백그라운드 작업, 무시)

## 4. 3화 점검

### 수치화

- 수정 파일: 4개
- 제거된 코드: `setInitialSelection` relay 방출 8줄

### 구체화

- `Driver.just`는 구독 즉시 방출하므로, `initialButtonTag`를 구독하는 순간 `setInitialSelection`이 호출되어 relay가 방출됐다. 시트가 화면에 뜨기도 전에 `onStatusUpdate`가 발화되는 이유였다.

### 행동화

- `output.initialButtonTag` → `setInitialSelection` → relay 방출 → `statusTapped` → `dismissTrigger` 경로를 코드 추적으로 파악

## 5. 배운 점 / 인사이트

- RxSwift `Driver.just`는 구독 즉시 동기적으로 방출한다. UI 초기화 목적으로 relay를 직접 방출하면, 그 relay가 다른 스트림에 연결된 경우 의도치 않은 사이드 이펙트가 발생한다.
- ViewModel init에서 상태를 초기화했다면, 구독 시점에서 relay를 다시 방출할 필요가 없다. UI 초기화(selectButton)와 상태 초기화(selectedStatus)는 별개로 처리해야 한다.

## 세션 3. 시간 설정 → 대시보드 전환 지연 수정

한 줄 요약:
- 시간 설정 완료 버튼 탭 후 대시보드로 넘어가기까지 서버 응답을 기다리던 문제를 fire-and-forget으로 해결했다.

## 1. 결론 (What / Product)

- 오늘 만든 결과물:
  - `TimeSettingViewModel.swift`: `completeSetup()`에서 `syncPillToServer`를 `Observable.zip`에서 분리해 fire-and-forget으로 처리
- 전/후 변화: 완료 버튼 탭 후 플로팅 뷰 출현까지 서버 응답 대기(수 초) → 로컬 작업 완료 즉시 출현
- 수치 또는 범위: 수정 파일 1개, 변경 라인 ~10줄

## 2. 배경 (Why / 3C)

### Customer

- 누구를 만족시켜야 했는가: 처음 약 설정을 완료하는 신규 사용자
- 그들이 원하는 것은 무엇이었는가: 완료 버튼을 누르면 즉시 다음 화면으로 넘어가야 함

### Competitor

- 기존 방식의 한계: `Observable.zip(syncPillToServer(...), setupNotificationAndSaveSettings())`으로 서버 동기화와 로컬 설정을 병렬 처리했지만, `syncPillToServer` 내부가 POST + PATCH 2개의 서버 요청이 직렬로 실행되어 전체를 블로킹
- 이번에 선택한 방향: 서버 동기화는 대시보드 진입을 막을 이유가 없다. 로컬 사이클만 생성되면 앱이 정상 동작하므로, 서버 동기화는 백그라운드에서 독립적으로 처리

## 3. 실행 (How / 4P)

### Product

```swift
// 수정 전
return Observable.zip(
    self.syncPillToServer(...),         // ← 완료 대기
    self.setupNotificationAndSaveSettings()
).map { _ in () }

// 수정 후
self.syncPillToServer(...)
    .subscribe()
    .disposed(by: self.disposeBag)      // ← fire-and-forget

return self.setupNotificationAndSaveSettings()  // ← 이것만 대기
```

`syncPillToServer`는 이미 `.catch { _ in .just(()) }`로 에러를 무시하므로 fire-and-forget 처리가 안전하다.

### Place

- `TimeSettingViewModel.completeSetup()` — 처음 약 설정 완료 시 실행되는 단일 진입점

## 4. 3화 점검

### 수치화

- 대기 시간: 서버 응답 시간(수 초) → 0 (로컬 작업만 대기)

### 구체화

- `Observable.zip`은 두 스트림이 모두 complete 될 때까지 기다린다. 서버가 느리면 그만큼 사용자가 버튼만 바라보게 된다

### 행동화

- `completeSetup()` → `syncPillToServer()` 내부 체인 확인 → 직렬 서버 요청 2개 발견 → zip에서 분리

## 5. 배운 점 / 인사이트

- `Observable.zip`은 모든 스트림이 완료될 때까지 블로킹한다. UI 진행을 막을 필요가 없는 서버 동기화는 zip에 넣지 않고 fire-and-forget으로 분리해야 한다.
- 서버 동기화의 목적이 "로컬 데이터를 서버에 반영"이지 "UI 진행의 선행 조건"이 아닌 경우, 비동기로 처리하는 것이 UX에 유리하다.
