# 개발로그 - 2026-05-12

## 세션 1. TestFlight 크래시 4건 수정 + PATCH /cycle 미전송 버그 수정

한 줄 요약:
- TestFlight 크래시 리포트 4건을 진단·수정하고, 약 사이클 데이터가 서버에 전송되지 않던 race condition 버그를 발견해 수정했다.

## 1. 결론 (What / Product)

- 오늘 만든 결과물:
  - `DayItem.swift`: `Hashable` id-only 재정의
  - `PillingApp.xcodeproj`: FirebaseAnalytics 제거, 위젯 버전 1.1.0 → 2.2.2 수정
  - `GoogleService-Info.plist`: 더미 plist → 실제 plist 교체
  - `TimeSettingViewModel.swift`: `syncPillToServer` fire-and-forget → `Observable.zip` 병렬 실행으로 변경
- 전/후 변화: 앱 실행 즉시 크래시 3종 제거 / 약 등록 시 cycle 데이터(active_days, break_days, cycle_start_date)가 서버 DB에 정상 저장됨
- 수치 또는 범위: 크래시 4건 → 0건, DB NULL 필드 3개 → 정상값

## 2. 배경 (Why / 3C)

### Customer

- 누구를 만족시켜야 했는가: TestFlight 베타 테스터(본인)
- 그들이 원하는 것은 무엇이었는가: 앱이 실행되고, 약을 등록하면 알림이 정상 동작해야 함

### Company

- 프로젝트의 현재 목표: TestFlight → App Store 배포 안정화
- 해결해야 할 문제: 4건의 크래시와 서버 사이클 데이터 누락
- 내 기여 지점: 크래시 근본 원인 진단 + 서버 연동 race condition 발견

### Competitor

- 기존 방식의 한계: `syncPillToServer`가 fire-and-forget이라 화면 전환 직후 disposeBag이 해제되면 PATCH 요청이 취소됨
- 이번에 선택한 방향: `Observable.zip`으로 서버 동기화와 알림 설정을 병렬 실행 후 둘 다 완료되면 화면 닫힘

## 3. 실행 (How / 4P)

### Product

#### 크래시 1 — DashboardCalendarView (2.2.1 build 13)

- 증상: `UICollectionViewDiffableDataSource.reconfigureItems` 내부에서 assertion 실패
- 원인: `DayItem`의 `Hashable` 자동 합성이 모든 stored property를 사용 → `status`가 바뀐 새 아이템이 snapshot에서 "다른 아이템"으로 인식됨
- 수정: `DayItem.swift`에 `==`와 `hash(into:)`를 `id`만 사용하도록 명시 재정의

#### 크래시 2~4 — Firebase 실행 크래시 (2.2.2 build 4/5/7)

- 증상: `FirebaseApp.configure()` 호출 시 `FIRApp.m:307` `isAppIDValid` 실패 → exception
- 원인: `GoogleService-Info.plist`의 `GOOGLE_APP_ID`가 `1:000000000000:ios:dummy` (더미 값) — `dummy`가 hex가 아니라 format validation 실패
- 중간 시도: FirebaseApp nil-check 추가 → 실패 / FirebaseAnalytics 제거 → 실패 (근본 원인이 plist)
- 수정: iCloud에 보관된 실제 `GoogleService-Info.plist`로 교체 (`GOOGLE_APP_ID: 1:612018457330:ios:c1e6e943f180a9b819de6b`)
- 참고: 파일은 `.gitignore`에 포함 — 빌드 전 iCloud에서 수동 복사 필요

#### 부가 수정

- 위젯(`DaillyWidgetExtension`) `MARKETING_VERSION` 1.1.0 → 2.2.2 (앱 버전과 일치)

#### 서버 cycle 데이터 미전송 버그

- 증상: 약 등록 완료 후 서버 DB의 `active_days`, `break_days`, `cycle_start_date`가 모두 NULL
- 서버 로그: `PATCH /pills/{id}/cycle` 요청 자체가 수신되지 않음
- 원인: `completeSetup()` flatMap 내에서 `syncPillToServer()`를 fire-and-forget(`subscribe().disposed(by: disposeBag)`)으로 호출 후 `setupNotificationAndSaveSettings()`를 반환. 알림 설정이 끝나면 화면이 닫히고 ViewModel이 `deinit`되어 `disposeBag`이 해제 → `POST /pills` 응답 직후 `PATCH /cycle`을 실행하기 전에 구독 취소됨
- 수정: `syncPillToServer`를 `Observable<Void>` 반환 함수로 변경하고, `Observable.zip(syncPillToServer(...), setupNotificationAndSaveSettings())` 으로 병렬 실행 → 둘 다 완료될 때까지 화면 닫히지 않음

```swift
// 수정 전
self.syncPillToServer(...)   // fire-and-forget, disposeBag에 귀속
return self.setupNotificationAndSaveSettings()

// 수정 후
return Observable.zip(
    self.syncPillToServer(...),
    self.setupNotificationAndSaveSettings()
).map { _ in () }
```

### Price

- 만족 신호: 시뮬레이터 빌드 성공 (BUILD SUCCEEDED, 에러 0건)
- cycle 데이터 수정 후 TestFlight 빌드를 올리면 서버 DB에 데이터가 채워지는지 E2E 확인 필요

### Place

- `TimeSettingViewModel.completeSetup()` — 복약 설정 완료 버튼 탭 시 실행되는 메인 체인
- `DayItem.swift` — 대시보드 캘린더 아이템의 동일성 판단 기준

### Promotion

- `syncPillToServer` 같은 "fire-and-forget처럼 보이지만 실제로는 ViewModel 수명에 의존하는" 패턴은 화면 전환 직전에 취소될 위험이 있다. Observable chain에 포함시켜야 한다

## 4. 3화 점검

### 수치화

- 크래시 4건 → 0건
- `DayItem` 동일성 판단 기준: 4개 프로퍼티 → 1개 (`id`)
- `PATCH /cycle` 전송 성공률: 0% → 예상 100% (다음 빌드에서 확인)

### 구체화

- Firebase 크래시는 실제 plist 없이 더미 값으로 4개 빌드를 태웠다. plist가 gitignore이면 빌드 전 복사 체크리스트가 필요하다
- `reconfigureItems` 크래시는 `Hashable` 자동 합성이 "동일성" vs "동등성"을 명확히 분리하지 않을 때 생기는 전형적인 실수다

### 행동화

- 크래시 리포트 스택 트레이스 → 소스 추적 → 단계별 가설 검증 (nil-check → Analytics 제거 → plist 교체)
- DB NULL 확인 → 서버 로그에서 요청 미수신 확인 → 클라이언트 코드에서 dispose race 발견

## 5. 배운 점 / 인사이트

- `UICollectionViewDiffableDataSource.reconfigureItems`는 snapshot 내 동일 아이템을 id로 찾는다. `Hashable`이 모든 프로퍼티를 사용하면 값이 바뀐 아이템을 "존재하지 않는 아이템"으로 인식해 크래시가 난다
- `GoogleService-Info.plist`는 format 검증이 엄격하다. hex segment가 아닌 값이 들어오면 `configure()` 시점에 exception이 발생한다. gitignore된 설정 파일은 빌드 전 체크리스트로 관리해야 한다
- Observable chain에서 fire-and-forget 패턴은 ViewModel 수명이 짧을 때 취소된다. "실패해도 UX 차단 없음"이 요구사항이더라도 완료를 보장하려면 chain에 포함시켜야 한다
