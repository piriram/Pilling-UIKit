## 세션 2. Pilling 서버 클린아키텍처 연동

## 1. 결론 (What / Product)

- 생성한 파일: 12개 (Domain Entity, Protocol, Infra DTO/APIService/Repository, UseCase 6개)
- 수정한 파일: `UserDefaultsKey`, `UserDefaultsManager`, `DIContainer`, `Config.xcconfig.template`, `Info.plist`
- 전/후 변화: 서버 API 6개 엔드포인트를 호출할 수 있는 Clean Architecture 레이어가 완성됐다

## 2. 배경 (Why / 3C)

- 서버는 `X-API-Key` 인증 기반으로 user 등록, device token 갱신, 약 등록/조회, 복용 기록 API를 제공
- 기존 로컬 전용 구조에 서버 레이어를 추가해야 했다
- 기존 `MedicationAPIService`/`CycleRepository` 패턴을 그대로 따라 RxSwift Observable 기반으로 구현

## 3. 실행 (How / 4P)

### 레이어별 구조

```
Domain
├── Entity/ServerPill.swift               # ServerPill, PillTakenRecord 도메인 모델
└── Protocol/PillingServerRepositoryProtocol.swift  # 인터페이스

Infra
├── Network/PillingServerAPI/
│   ├── PillingServerDTO.swift            # Request/Response Codable 구조체
│   └── PillingServerAPIService.swift     # URLSession 기반 HTTP 클라이언트 + PillingServerError
├── PillingServerRepository.swift         # 프로토콜 구현체
└── UseCase/
    ├── RegisterUserUseCase.swift
    ├── UpdateDeviceTokenUseCase.swift
    ├── DeleteServerUserUseCase.swift
    ├── RegisterServerPillUseCase.swift
    ├── FetchServerPillsUseCase.swift
    └── RecordServerPillTakenUseCase.swift
```

### 핵심 결정

- API Key: `Config.xcconfig` → `Info.plist $(PILLING_API_KEY)` → `Bundle.main` 읽기 (MFDS와 동일 패턴)
- serverUserID/serverPillID: `UserDefaultsKey`에 케이스 추가, `UserDefaultsManager`에 save/load 메서드 추가
- DIContainer에 `pillingServerAPIService`, `pillingServerRepository` lazy 추가 + 6개 make 메서드

## 4. 배운 점

- 같은 패턴의 APIService를 두 개 이상 관리할 때 URL 구성 방식(path 기반)을 범용 `request(method:path:body:responseType:)` 하나로 통일하면 반복이 줄어든다
- `Encodable?` 타입으로 body를 선택적으로 처리하면 GET/DELETE도 같은 메서드로 커버 가능하다

## 세션 3. 서버 연동 호출 시점 연결 + 빌드 검증

한 줄 요약:
- 클린아키텍처 레이어를 실제 앱 흐름에 연결하고, 시뮬레이터 빌드 및 실행까지 검증했다.

## 1. 결론 (What / Product)

- AppDelegate, TimeSettingViewModel, DashboardViewModel 3곳에 서버 호출 시점 연결 완료
- `Config.xcconfig`에 실제 API 키 입력 완료
- `xcodebuild` + `xcrun simctl` 로 빌드 성공, 시뮬레이터 실행 확인

## 2. 배경 (Why)

- 세션 2에서 레이어는 완성됐지만 실제 호출 트리거가 없었다
- 앱 흐름의 3개 시점(앱 실행 시, 복약 설정 완료 시, 복용 버튼 탭 시)에 서버 호출을 붙여야 서버 알림이 동작한다

## 3. 실행 (How)

### 연결된 흐름

| 시점 | 호출 | 처리 방식 |
|------|------|----------|
| APNs 토큰 수신 | `POST /users` | 409 conflict → `PATCH device-token` fallback |
| 복약 설정 완료 | `POST /users/{id}/pills` | 반환 pill_id UserDefaults 저장 |
| 복용 버튼 탭 | `POST /pills/{id}/taken` | fire-and-forget, 로컬 처리 차단 없음 |

### 핵심 결정

- `user_id` = `UIDevice.identifierForVendor?.uuidString` — 재설치 후에도 동일 디바이스면 같은 ID
- `syncPillToServer`는 로컬 사이클 생성 성공 후 별도 체인으로 실행 — 서버 실패가 로컬 UX 차단 안 함
- `recordPillTakenOnServer`도 동일 원칙 — 서버 오류 시 사용자 피드백 없이 로깅

### Xcode 파일 추가 이슈 해결

- 처음엔 `.pbxproj` 수동 편집 필요하다고 판단했으나, 프로젝트가 `PBXFileSystemSynchronizedRootGroup`(Xcode 16) 방식 사용 중임을 확인
- 해당 방식은 지정 폴더 내 모든 파일을 자동으로 빌드 타깃에 포함 — 수동 추가 불필요

## 4. 배운 점

- `PBXFileSystemSynchronizedRootGroup`은 Xcode 16에서 도입된 디렉터리 기반 자동 파일 포함 방식이다. 신규 파일을 폴더에 추가하기만 하면 빌드에 자동 반영된다
- 서버 연동을 로컬 흐름과 분리(fire-and-forget)하면 서버 장애가 앱 UX에 영향을 주지 않는다
- APNs 등록 → 사용자 등록 흐름은 409 처리를 통해 재설치/신규 설치 모두 커버할 수 있다

## 세션 4. device_token 연동 버그 수정 및 서버 E2E 검증

한 줄 요약:
- 시뮬레이터 APNs 미지원 이슈를 파악하고, 서버와 실제 통신해 user/pill 등록 흐름을 검증했다.

## 1. 결론 (What / Product)

- 서버 DB에 user 등록(201), device_token 갱신(200), pill 등록(201) 확인
- `hasRealAPNsToken` 플래그 도입으로 실기기/시뮬레이터 token 처리 분리

## 2. 배경 (Why)

- 서버에서 401/403 + DB 0건 → API 키 문제가 아니라 APNs 콜백 미실행 문제였다
- 시뮬레이터에서는 `didRegisterForRemoteNotificationsWithDeviceToken`이 절대 호출되지 않아 user 등록 자체가 안 됐다
- 또한 빈 문자열(`""`)로 device_token을 등록하는 버그도 있었다

## 3. 실행 (How)

### 수정 이력

| 버그 | 원인 | 수정 |
|------|------|------|
| user 미등록 | APNs 콜백 미실행 | `didFinishLaunchingWithOptions`에서 `registerUserIfNeeded()` 추가 |
| device_token 빈 문자열 | placeholder 없이 `""` 전송 | `identifierForVendor`를 placeholder로 사용 |
| placeholder가 실 토큰 덮어씀 위험 | `updateDeviceTokenIfPlaceholder` 매 실행 | `hasRealAPNsToken` 플래그로 실 토큰 보호 |

### 환경별 동작

| 환경 | device_token |
|------|------|
| 시뮬레이터 | `identifierForVendor` UUID (APNs 불가) |
| 실기기 | APNs 콜백 64자 hex, 이후 placeholder 전송 차단 |

## 4. 배운 점

- 시뮬레이터에서 APNs 관련 콜백은 절대 호출되지 않는다. APNs 의존 흐름은 반드시 `didFinishLaunchingWithOptions` fallback을 함께 설계해야 한다
- device_token처럼 "언젠가 업데이트될 값"은 초기 등록을 placeholder로 하고, 실제 값 수신 시 갱신하는 패턴이 안전하다
- 서버와 통신이 성공해도 의미 있는 값인지 확인해야 한다 (200 OK지만 UUID 토큰은 APNs 발송 불가)

## 세션 5. updateDeviceTokenIfPlaceholder 제거

한 줄 요약:
- 앱 실행마다 UUID를 device_token으로 덮어쓰는 버그를 발견하고 원인 함수를 제거했다.

## 1. 결론 (What / Product)

- `AppDelegate`의 `updateDeviceTokenIfPlaceholder()` 함수 및 호출부 삭제
- 이후 device_token 갱신은 `didRegisterForRemoteNotificationsWithDeviceToken` 콜백만 담당

## 2. 배경 (Why)

- 서버 DB에서 기존 유저 D92B75A5의 device_token이 36자 UUID 그대로였다
- 서버 로그에서 PATCH /device-token 요청은 성공했지만 전송된 값 자체가 UUID
- `updateDeviceTokenIfPlaceholder`가 `hasRealAPNsToken == false`이면 매 실행마다 UUID로 PATCH를 보내고 있었다

## 3. 실행 (How)

- 원인: `updateDeviceTokenIfPlaceholder`는 실 APNs 토큰이 없을 때 서버에 placeholder(UUID)를 능동적으로 PATCH하는 함수
- 문제: 서버는 이미 최초 등록 시 placeholder를 가지고 있다. 추가로 덮어쓸 이유가 없다
- 해결: 함수와 호출부 전체 삭제. device_token 갱신은 APNs 콜백 하나로 단일화

## 4. 배운 점

- "실 토큰이 없을 때 placeholder로 갱신"은 의도와 반대로 동작한다. 갱신은 실 값이 생겼을 때만 해야 한다
- placeholder는 초기 등록(POST)용이고, 갱신(PATCH)은 실 데이터 수신 시에만 트리거되어야 한다

## 5. 다음 액션

- [ ] 실기기에서 APNs 콜백 → 64자 hex 토큰 서버 저장 재검증
